# B1×G5 不是取舍：本机上那道门**已经**是红的，而且死在行尾

- 交付：`scripts/g5_pin_probe.py`（8 自检）+ 本报告

## 1. 第 11 轮留下的那句结论，缺一个前提

> 修 B1 **必然**让 G5 transfer 证据的 `source_fingerprints` 失配，所以这是二选一。

这句话讲的是**内容**：改一个字节，哈希就变。它没有讲**状态**：这些哈希是在什么样的检出上算的。

本仓库 `core.autocrlf=true`，`.gitattributes` 只为 `fixture.py` 一个文件钉了 `eol=lf`。所以其余被钉住的文件在 Windows 上检出时是 CRLF，而记录里的哈希是 LF。**在任何人动手之前，两边就已经不相等。**

## 2. 实测：6 个被钉文件，5 个只差行尾

```
file                                            verdict      disk/blob   detail
src/autoresearch/contracts.py                   match        3524/3524   live bytes equal the committed blob
src/autoresearch/bounded_study_ledger.py        eol_only    46091/45406  685 CRLF account for all 685 extra bytes  recorded=blob
src/autoresearch/scheduling_threshold_policy.py eol_only     2240/2184    56 CRLF account for all 56 extra bytes
src/autoresearch/scheduling_kernel.py           eol_only     5200/5083   117 CRLF account for all 117 extra bytes  recorded=blob
scripts/run_scheduling_policy_transfer.py       eol_only    47408/46647  761 CRLF account for all 761 extra bytes
scripts/verify_scheduling_policy_transfer.py    eol_only    55122/54256  866 CRLF account for all 866 extra bytes
EXIT 2 (EOL_ONLY_GATE_ALREADY_RED)
```

判据不是「大小差不多」，而是**把盘上字节的 CRLF 全部换成 LF 之后哈希等于 blob 哈希**，且 `字节差 == CRLF 个数` 逐个成立（685=685、56=56、117=117、761=761、866=866）。这是算术，不是推断。

`recorded=blob` 那两行更关键：`bounded_study_ledger.py` 记录的 `1d39b54d…` 与 `scheduling_kernel.py` 硬编码的 `3a335e10…` **都等于各自 LF blob 的哈希**。也就是说这些记录是在 LF 检出上做的，与 `contracts.py` 恰好是 LF（所以唯一 `match`）互相印证。

## 3. 这条门为什么现在必然红

`run_scheduling_policy_transfer.py` 的 `_environment()` 做两件事：

1. `_fingerprints()` 读**工作树字节**算哈希；
2. 断言 `sources['src/autoresearch/scheduling_kernel.py'] == '3a335e10…'`，再用存下的 review JSON 做 `canonical(current) == canonical(expected)`。

第 2 步在本机读到的是 `493f0a4f…`（CRLF 版），**与 B1 无关**、与有没有人改 `bounded_study_ledger.py` 也无关。`bounded_study_ledger.py` 只影响第 1 步里那一个键，而 `scheduling_kernel.py` 这枚硬编码断言先就过不去。

## 4. 于是二选一在本机退化成「没有代价」

| 检出形态 | 证据现状 | 修 B1 的代价 |
|---|---|---|
| Linux / LF（记录产生的地方） | 6 个钉全部命中，证据可复核 | **真实代价**：改了 `bounded_study_ledger.py`，那一枚钉就失效 |
| 本机 Windows / CRLF | 5 个钉已经是 `eol_only`，门本来就过不去 | **0**（没有任何东西可再失去） |

所以第 11 轮那句「必然破坏」只对 LF 检出成立。**在本机上，修 B1 不会拿走任何还活着的东西**——但同样地，本机也从来没有能力复核这份证据，所以也**不能**用本机把 G5 记成「通过」。

## 5. 还有一条没人列过的路：让两边都保住

第 11 轮只给了 A（标记为历史证据，改文件）与 B（不改，20 个入口继续死）。实测之后多出一种：

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A | 把 G5 证据标成历史（绑定 `62f09ed`），再改 `bounded_study_ledger.py` | Linux 上失去那 7 个文件的字节级可复核性 | 证据仍可读，但不再能重算比对 |
| B | 不改，20 个入口保持不可用 | P2 的调用记录只能走不依赖该链的独立路径 | 无 |
| **C** | **改 B1，同时在 LF 检出（或给这 7 个文件加 `eol=lf`）里复核 G5** | 一次 `git worktree add -c core.autocrlf=false` 或 7 行 `.gitattributes` | 需要改 `.gitattributes` 或新增工作树，属环境变更；且本机仍需 `fcntl` 抽象才能真正跑起来 |

C 的关键点：**它不需要改校验器，也不需要把证据标成历史**。它只是把「用哪种字节去比对」这件事说清楚。我本轮**不执行 C**（会改工作树形态或新增检出，超出零成本范围），也不建议在没有 Owner 决定的情况下擅自给 `.gitattributes` 加规则——加规则会让 7 个文件在下次检出时被重写，那是另一件需要先说清的事。

## 6. 这个发现不证明什么

- **不证明** G5 的研究结论有错。证据在 LF 上仍然自洽，`recorded=blob` 就是证据。
- **不证明** 修 B1 就万事大吉。就算修好 `fcntl`，本机 CRLF 仍会让这枚门红——修 B1 只是让 20 个入口能导入，不等于 G5 能复核。
- **不证明** 第 11 轮的测量有错。它测的是「谁依赖这个模块」，与本轮测的「钉住的字节是什么」是两件事，互不推翻。
- 唯一可以确定的是：**「必然后果」这个措辞在这里是过度断言**，因为它依赖一个没写出来的前提（LF 检出）。

原问题「是否同意把 G5 证据标成历史证据、以换取修改 `bounded_study_ledger.py`」，现在可以换成：
