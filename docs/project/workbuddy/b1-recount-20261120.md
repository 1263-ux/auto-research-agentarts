## 一句话

前 13 轮用的「20 个入口在 Windows 上判死、根因只有 `fcntl` 一条」是**低估**：真值是 **26 个**，根因 **两条**（`fcntl` 与 `resource`）。第 14 轮提出的选项 C（改 B1 + 按 LF 检出）**不成立**，因为必须改的那个文件本身就在被钉列表里。

## 一、选项 C 被证伪

第 14 轮的推理是：6 个被钉文件里 5 个「只差行尾」，所以把 CRLF 换回 LF 就能让指纹重新对上，于是「改 B1」与「保住 G5 证据」可以两全。

这句话漏掉了一个前提：**必须被改的那个文件，本身就在被钉列表里。**

`scripts/run_scheduling_policy_transfer.py:44`：

```
SOURCE_FILES = ('src/autoresearch/contracts.py', 'src/autoresearch/bounded_study_ledger.py', ...)
```

B1 的根因是 `bounded_study_ledger.py:9` 的模块体 `import fcntl`。修它必然改写这个文件的字节；行尾规范化只能让「没人碰过的文件」重新对上，对「被改过的文件」无效——内容哈希与行尾无关。

`verify_scheduling_policy_transfer.py:579-588` 是最终裁决处：它拿 `Path(__file__).resolve().parent.parent`（**活工作树**）逐文件读字节，与存档指纹比对，不等即 `A frozen source file changed.`。

**实测**（`scripts/g5_pin_probe.py`，自检 8/8 → **15/15**）：

| 判定 | 值 |
|---|---|
| 被钉文件 | 6 个 .py（5 `eol_only` + 1 `match`） |
| 模块体 `import fcntl` 的被钉文件 | **1 个：`src/autoresearch/bounded_study_ledger.py:9`** |
| 结论 | `B1 repair is NOT free` |

探针新增的判定不硬编码，而是用 AST 从被钉文件自己的字节里读出「谁在模块体导入 POSIX 模块」。函数内导入不算——那种模块仍可导入，只是执行到才失败，修法不同（第 11 轮的教训）。

**所以 B1×G5 仍是取舍，且选项 C 必须从列表里划掉。** 剩下的真实选项是：

- **A**：标历史证据为不可在本机复核 + 改 B1
- **B**：都不动（26 个入口继续死）
- **D**（本轮新增，见第三节）：不改任何被钉文件，用兼容层注入

## 二、判死数是 26，不是 20

`scripts/portability_scan.py:230`（修正前）：

```python
unguarded = sorted({m for name in reached for m, _ in graph[name]["top"]})
```

`graph` 只装 `src/autoresearch/*.py`（第 201 行），**入口脚本自己不在里面**。于是脚本自身的模块体 POSIX 导入从未被统计：一个只写 `import resource`、不 import `autoresearch` 的脚本，`reached` 为空、`unguarded` 为空，被判为**活的**。

**6/6 实测为真死，且模块名与修正后的归因逐个吻合。** 判死集合 **20 → 26**，`population_size` 仍 149、`population_sha256` 不变（入口集合没动，改的只是判定）。

新增两个字段，因为「范围」是这个数字最容易读错的地方：

- `hard_blockers: ['fcntl']` —— **只覆盖 `src/autoresearch`**，字面为真，读成「全部硬阻塞」就是错的

`project_autonomy_guard.py` 就在这 6 个里。状态文档一直写「guard 在 Windows 因 fcntl 不可用」，原因从第 1 轮起就在本机，但**直到本轮它才被计入统计**——它是第 21 个，不在前 13 轮说的 20 个里。

自检 **13/13 → 17/17**，新增 4 条：入口自身模块体 POSIX 导入算阻塞、归因到入口而非模块、脚本级阻塞不进 src 范围汇总、活入口的 `own_posix` 为空。

## 三、选项 D：兼容层实测，能救 26 个里的 21 个

不改任何被钉文件，把 `fcntl` 实现以 `PYTHONPATH` 注入。`fcntl` 在这条链上的用法极窄：`flock(fd, LOCK_EX | LOCK_NB)` 与 `LOCK_UN`，3 个文件共 6 处调用。

兼容层用 `msvcrt.locking` 实现（`runs/round16-20261120/shim/fcntl.py`）。**语义差异必须写清**：POSIX `flock` 锁整个文件且与偏移无关，`msvcrt` 只能从当前偏移锁字节范围，故每次先 seek 到 0 锁 1 字节、再恢复调用方偏移。

实测三件事：

1. **真的能跑业务逻辑**：`run_research_project.py status --workspace …` 从 `RC=1`（import 失败）变成输出 `{"ok": false, "code": "PROJECT_NOT_FOUND", ...}`。注意它返回 `rc=2` —— 这是业务错误码，不是崩溃（第 15 轮 `rc` 有歧义那件事的又一例）。
2. **锁真的互斥**：持锁进程运行中，第二个进程 `LOCK_EX|LOCK_NB` 得到 `BLOCKED 13`（EACCES）；持锁进程退出后重新 `ACQUIRED`。
3. **空文件也能锁**：`ACQUIRED_ON_EMPTY`。这是 `msvcrt` 区域锁的可疑点（没有字节可锁），实测不成立，少一个失败模式。

**26 个判死入口的 `--help` 矩阵**（每个入口跑两次，无桩 / 有桩）：

| | 无桩 | 有桩 |
|---|---|---|
| `--help` rc=0 | **0 / 26** | **21 / 26** |
| stderr 仍含 `fcntl` | 26 | **0** |

剩余 5 个全部死在同一件事：`ModuleNotFoundError: No module named 'resource'` —— `run_concrete_reproduction.py`、`run_cpu_transfer_benchmarks.py`、`run_g4_group_candidate.py`、`run_tabular_transfer.py`、`verify_native_group_candidate.py`。其中 2 个（`run_concrete_reproduction`、`run_tabular_transfer`）同时有 `fcntl` 与 `resource` 两条死因。

**所以 B1 不是一个阻塞，是两个**：`fcntl` 罩 23 个入口，`resource` 罩 5 个，交集 2 个，并集 26 个。此前所有「修掉 fcntl 就能让入口活过来」的表述都只对 21/26 成立。

**选项 D 不是修复**：它靠外部注入，换台机器没有它照样死；它是「在不碰被钉文件的前提下，让本机能验证业务逻辑」的通道。要真可移植，仍得改代码——那就是选项 A。

## 四、负结果与自踩

- **选项 C 不成立**，这是本轮推翻的第 14 轮结论。第 14 轮的「5/6 只差行尾」本身测对了，但它只回答了「没人碰过的文件能不能对上」，没回答「被改的文件能不能对上」。
- **判死数低估 6 个**（20 → 26，−23% 偏差）。根因不是我读错了数据，是扫描器的**作用域**错了：入口脚本不在被扫描的模块图里。这是第 11/12/13 轮同族错误的第四次，共同点是「观测是真的、解释多走了一步」：
  - 11 轮：`from . import a, b` 解析漏 → 判活
  - 12 轮：正则要求 `**` 紧跟冒号 → 判卡缺字段
  - 13 轮：20 s 超时 → 判挂起
  - 16 轮：入口不在 graph → 判活
- **第 11 轮「fcntl 是唯一导入期阻塞」这句探针结论，作用域也只有 src**：空桩让 `status` 输出结构化 JSON，说明**经 ledger 那条链**只有 fcntl；它没说入口自身还可能有别的。本轮 5 个 `resource` 就是这句话被读宽之后的代价。
- 自检没抓到根因是**夹具形状不完备**：原夹具的每个入口都 import 了 `autoresearch`，所以「入口自身不在 graph」这个洞永远走不到。补的夹具 `scripts/own_resource_entry.py` 只写一行 `import resource`，不 import 任何项目模块——同族于第 15 轮「夹具路径形状与真实调用不一致」。
- 矩阵跑 52 次子进程约 2 分钟，两次被前台超时转后台。未踩第 14 轮那个 `subprocess.run(timeout=)` 杀进程阻塞的坑（本轮不设 timeout）。
