## 2. 关键约束：不写第二份 BM25 常量

本仓库已有一处已知隐患：排序有两份实现（`retrieval_lexical.retrieve` 用字面量 `k1=1.2,b=.75,20`；`relevance_retrieval_adapter.retrieve` 读 `COMPARISON`）。W05a 若再写一份，就是第三份。做法：

- 模块把 `k1/b/top_k/candidate_depth/fb_docs/fb_terms/orig_weight/tokenizer/tie_break` 全部做成**显式数据** `PROTOCOL`，不写字面量进公式；
- 自检 F1 逐项断言 `PROTOCOL` 与 `relevance_retrieval_adapter.COMPARISON` **相等**，两侧任一改动都会红；
- 自检 F1 在**合成语料**上比对 `bm25_scores` 与 `adapter.retrieve(..., "bm25")` 的排序（4 条查询 + 1 条带排除），排除情形也逐项相同；
- `tokens()` 与 `lexical.tokens()` 在 5 组刁钻输入（`Alpha_Beta 42!`、`ünïcode 42`、纯空白等）上等价。

这不是「口径一致」的结论——只是**同一输入上两条代码路径给出同一排序**这一条窄事实，且只在合成夹具上验过。

## 3. 最重要的一条发现：F2 漏了一个会改数的字段

卡 F2 冻结了 `fb_docs=20`、`fb_terms=10`、`orig_weight=0.5`，但**没有说明扩展词表怎么选**。两种读法都符合 RM3 文献：

- `combined_top_k`（Indri/Lemur 的默认读法）：把 P(w|Q) 与 P(w|R) 合并后取权重最高的 `fb_terms` 个，**原始查询词可能被挤掉**；
- `always_retain`：先取 top-`fb_terms`，再把被挤掉的原始查询词补回（总数可超 `fb_terms`）。

同一个夹具上两者给出不同结果（合成夹具，**不是研究结果**，`DRIFT_DOCS`：4 篇，查询 `alpha beta`）：

| 配置 | 排序 | 参与打分的词 | 被丢弃的原始词 |
| --- | --- | --- | --- |
| A 臂（单路 BM25） | `e1 e4 e2 e3` | alpha, beta | — |
| combined_top_k, fb_terms=1 | `e2 e3 e4` | gamma | **alpha, beta** |
| combined_top_k, fb_terms=10 | `e4 e2 e3 e1` | gamma, alpha, beta | 无 |
| always_retain, fb_terms=1 | `e4 e2 e3 e1` | gamma, alpha, beta | 无 |
| always_retain, fb_terms=10 | `e4 e2 e3 e1` | gamma, alpha, beta | 无 |

三点都在表里：

1. `e1`（唯一同时命中两个查询词、且不含 gamma 的文档）在 A 臂排第 1，在 `combined_top_k fb_terms=10` 下**掉到第 4**，在 `fb_terms=1` 下**直接消失**。这正是卡里已声明的「查询漂移」风险，现在它有了可复算的演示。
2. **策略不同 → 结果不同，但只在窄条件下分叉**：`fb_terms=1` 时 combined 只返回 3 篇（`e1` 消失），always_retain 返回 4 篇；`fb_terms=10` 时两者一致。所以这不是「策略总是差很多」，而是「**在小扩展预算或小词表上差**」——恰好是最容易被当成调参空间的地方。
3. **`always_retain` 会让 `fb_terms` 退化**：两行完全相同，因为补回原始词后扩展预算不再约束结果。也就是说，若选 `always_retain`，卡里那个 `fb_terms=10` 在小词表语料上可能是个空参数。

**处理**：不擅自改卡（F2 是 frozen 字段，改冻结字段属 Owner 权限）。模块同时实现两种策略，默认 `combined_top_k`（更接近原文献），并把实际使用的策略写进 `diagnostics.original_term_policy`，任何一份结果都无法谎报自己用了哪种。**W05 执行前，F2 必须补一个 `original_term_policy` 字段并由 Owner 冻结**，否则两个实验室拿到两套数都算合规。

## 5. 负结果与自查缺陷（保留，不改写）

1. **夹具写错一次**：初版 `"gamma" * 30` 在 Python 里是**字符串直接拼接**，生成一个 150 字符的巨型 token，而不是 30 个 `gamma`。F9 因此报 `dropped=['beta']`，我最初误以为是权重算错。修法 `" gamma" * 30`。教训：手写语料里凡是要重复词，必须带分隔符；看起来「只是夹具」的错会伪装成算法错。
2. **断言写错一次**：「排除后候选数 = 语料篇数 − 1」是错的——`candidate_count` 统计的是**有得分**的文档，不是存在的文档。改成与「不排除时」的候选数相减。
3. **两次失败都不是模块错**。这类「先怀疑实现、其实是夹具」的顺序，与前几轮「先跑真实对象再看自检」是同一类教训的反面：合成夹具本身也要先被验证。
4. 未做的事（如实列出）：没有在冻结语料上跑过；没有验证 RM3 是否真的提升 mrr@10（本包没有授权，且 M1b 已证同语料上量级差 ≤ MDES）；没有锚定 RM3 的原实现版本/许可（卡「未覆盖项 2」仍在）；稠密检索仍未覆盖。
