# W05 门禁 R13/R14：把「F2 缺字段」变成机械判定

- **轮次**：周期对齐检查第 9 轮（2026-11-20 15:07 起 +08）
- **性质**：工程与只读核对。零研究行动、零模型、零拟合、零现金、零推送。
- **上一轮遗留**：第 8 轮反查出 F2 冻结了 `fb_terms=10` 却没定「扩展词表怎么选」，当时只写在报告和记忆里——**那就是还没修**。本轮把它做成门禁，任何人拿这张卡都要过这一关。

## 1. 为什么不是「直接给卡补个值」

补上 `original_term_policy: "combined_top_k"` 会让卡变绿，但那是我替 Owner 做决定，而且是把一个会影响结果的参数塞进 frozen 字段。正确做法是：**卡继续红着，且红得可读**——机器能量出「这一项还没定」，人不必靠通读散文去发现。

## 2. 三态判定，而不是 pass/fail

原来每条规则只有 pass/fail，`fail` 一律 exit 1。但「Owner 还没选」和「卡写错了」是两种问题，混在一起会让未签的草案看起来像损坏的文件。新增 `pending`：

| 状态 | 含义 | 对退出码的影响 |
| --- | --- | --- |
| `pass` | 规则满足 | — |
| `pending` | 结构正确，等 Owner 决定 | 维持 `EXIT 2`（草稿可评审） |
| `fail` | 规则被违反 | `EXIT 1`（不得进入执行） |

## 3. 两条新规则

**R13_term_policy** —— F2 必须把选择策略编码成闭集字段 `{combined_top_k, always_retain}`：

| 卡里的值 | 判定 |
| --- | --- |
| 字段缺失 | `FAIL`（不是「没写就默认」，是「没写就不知道」） |
| `null` | `PENDING`（已登记未定） |
| 闭集外的值 | `FAIL` |
| 闭集内但**与模块默认不同** | `FAIL`：「卡上说 X，`w05a_rm3.PROTOCOL` 说 Y」 |

最后一行是本轮最实用的一条。没有它，Owner 在纸上选 `always_retain`、代码继续跑 `combined_top_k`，两边都不报错，出来的数却对不上卡。**决定必须落到代码里才算数。**

**R14_arm_matches_module** —— F2 的 7 个数字（`k1/b/top_k/candidate_depth/fb_docs/fb_terms/orig_weight`）必须与 `scripts/w05a_rm3.PROTOCOL` 逐项相等（浮点 `1e-12`）。这是第 8 轮「不写第三份 BM25 常量」的延伸：卡与模块也不能各说各话。模块加载失败 → `FAIL`（不静默跳过）。

## 4. 卡上的改动（只补编码，不动已冻结数值）

- F2 增 `arm`：把散文里已冻结的 7 个数字**原样转写**成机器可读，供 R14 比对；
- F2 增 `original_term_policy: null`：`null` 明确表示「已登记、未决定」，不是冻结值；
- 正文加「F2 修订提案（pending，未生效）」一节：两选项的读法、`fb_terms=1` 时的 3 篇 vs 4 篇、以及 `always_retain` 让 `fb_terms` 退化的副作用，供 Owner 一次性决定；
- 字段总览表 F2 行改为「frozen（数值）/ **策略未定**」。

## 6. 负结果与保留的疑点

1. **`EXIT 2` 的语义变宽了**：现在包含「有 pending」，不只是「有 open/blocked 或未签字」。任何按旧口径读 `EXIT 2` 的脚本仍能跑，但若有人统计「剩余阻塞数」，需要读 `check.json` 的 `state` 而不是退出码。旧报告里「EXIT 2」的历史记录不追溯改写。
2. **模块默认值本身是个隐患**：`PROTOCOL["original_term_policy"]` 默认 `combined_top_k` 是我的选择，不是 Owner 的。R13 现在只能保证「卡与默认一致」，不能保证「默认是对的」。执行时若 Owner 选另一条，改常量即可，但改完必须重跑本门禁。
3. **`w05a_rm3` 加载失败 → R14 FAIL** 这条路径没有独立注入测试（要临时移走文件），属未验项，已在此登记。
4. 未做的事：没有在冻结语料上跑过任何一臂；没有替 Owner 选策略；没有把 `pending` 降级成提示。
