## 2. 关键发现：CLI 主入口在 Windows 导入即失败（影响所有 status/selection-context/advance-recipe 实测）

- 现象：`.venv/Scripts/python.exe scripts/run_research_project.py --help` 在每个子命令进入 argparse **之前**就抛 `ModuleNotFoundError: No module named 'fcntl'`，退出码 1。
- 导入链（源码逐行核实）：
  - `scripts/run_research_project.py:15` → `from autoresearch.project_controller import ProjectController`
  - `src/autoresearch/project_controller.py:8` → `from . import project_design, saved_study_reference`
  - `src/autoresearch/saved_study_reference.py:11` → `from .bounded_study_ledger import BoundedStudyLedger`
  - `src/autoresearch/bounded_study_ledger.py:9` → `import fcntl`（**无条件顶层导入，fcntl 是 POSIX 专属，Windows 无此模块**）
- 独立验证：`.venv/Scripts/python.exe -c "import fcntl"` → 同样 `ModuleNotFoundError`（RC=1）。`export_project_report.py --help` 经 `project_report → project_workbench:18 → project_controller → … → fcntl` 同一链失败。
- 影响：CLI 的 `status` / `selection-context` / `advance-recipe` / `next` / `advance` 以及报告导出入口，在本机 Windows 均不可运行；本轮无法给出它们的「命令成功回执」。这不是接线缺失，而是**运行平台兼容性阻塞**。从 `continuous-status.md:17` 可知官方校验用的是 `.venv`（Python 3.12.14），但平台是 Windows 11；历史 Linux/POSIX 环境的实跑证据见 `integration.md:68-82` 的 A29/A30 记录（当时环境可跑），不能据此声称当前 Windows 可跑。
- 对 W03 的处置：对照框架按「源码契约 + POSIX 可运行假设」设计；若要在本机真正复跑 M4 对照，需先解决 fcntl（例如改用 POSIX 环境 / 提供 Windows 兼容 shim），这一项作为阻塞上报主控，**不在本轮自行改造项目源码**（会改冻结/共享实现，超出允许写文件范围）。
- 回执证据：`runs/continuous-20261120/integration/cli-help.txt`、`status-a14.txt`、`export-help.txt`、`fcntl-check.txt`（见 §6）。

### 3.3 CLI `advance-recipe`（写入，本轮禁止执行）

- **真实路径**：命令定义 `scripts/run_research_project.py:101-106`（`--workspace/--request-id/--recipe/--expected-state-version` 必填，`--need` 默认 `next_check`）；分发 `run_research_project.py:188-192`：读配方（严格 JSON，≤`MAX_RECIPE_BYTES=64KiB`，`parse_json`，`code=INVALID_RESEARCH_RECIPE`）→ `ProjectController.advance_recipe(...)` → `src/autoresearch/project_controller.py:1202-1212` → `_advance(...)`（`1214-1294`）。
- **命令样例**（**本轮仅记录，不执行**）：
  `.venv/Scripts/python.exe scripts/run_research_project.py advance-recipe --workspace runs/<project> --request-id recipe-step-1 --recipe examples/research-recipes/tabular-group-first.json --need next_check --expected-state-version <从 status 读取的 state_version>`
- **读写边界**：**写入**——冻结父 request（`controller_requests[]`，命令身份 `controller.advance_recipe`），`state_version += 1`，派生 child 并最多执行一个原 `step/read_evidence` 子请求（`project_controller.py:1271-1292`）。配方本身确定性、不调用模型（proposal.provider=`operator_assistant` / “no model”，`research_recipe.py:128`），不下载来源、不训练、不直接加额度；但会推进状态，**本轮不执行**。
- **身份/恢复机制**（代码依据充分）：
  - 同 request ID 走 `_parent()` 命中旧父记录（`project_controller.py:1205-1206, 323-325`）：要求旧命令 `controller.advance_recipe`，否则 `IDEMPOTENCY_CONFLICT`；
  - `advance_recipe` 恢复时用**旧父的 `selection_context`**重编译配方（`1209`），保证「原配方 + 原 need + 原 context」一致；

  - `expected_state_version` 必填且须等于当前（`1261-1262`，`STALE_STATE`），这是乐观并发/版本门。
- **预算门位置**：`STALE_STATE` 版本门 `1261-1262`；额度耗尽由 `_selection_context`（`82,209-218`）产 `BUDGET_EXHAUSTED` blocker 使候选不可执行；另有 `EXECUTION_UNKNOWN`（`1257`）、`PROJECT_BUSY`（`1259`）、`CODE_CHANGED`（`1263`）等门禁。这些门是「配置选择/执行协调」，不是新预算来源。
- **判定**：**已接线（源码）**，恢复机制真实存在；当前 Windows **不可运行**（同 §2）。**本轮未执行任何 advance-recipe**。
