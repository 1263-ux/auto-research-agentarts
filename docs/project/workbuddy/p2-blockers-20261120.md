## 1. 为什么阻塞列表值得单独一条规则

第 12 轮补的是「清单是否忠实于卡片」。清单 `not_verified` 里还剩两条：`blockers list contents` 与 `whether downstream dependencies exist in the current environment`。前 13 轮把 `blockers` 当自由文本传下来，没有人问过**它现在还是不是真的**。

这个问题有决策后果：阻塞列表正是让 Owner 伸手去「装一堆东西」的东西。如果其中一半描述的是已经变化的环境，那这份列表不是谨慎，是噪音；反过来，如果列表都成立，那么 Owner 的一次授权能解锁多少张卡，是可以先算出来的。

## 2. 能机械判定的只有一类，那就把这一类判到底

25 条 → 实际 **29 条**（第 10 轮转写时的工作数字是 25，真实条数 29）。逐条分类：

| 判定 | 条数 | 含义 |
|---|---|---|
| `confirmed` | **7** | 点名的模块在本机确实不存在，阻塞成立 |
| `stale` | **0** | 没有一条描述的是「已经变化的环境」 |
| `undecidable` | **22** | 数据 / 许可 / 凭据 / 上游版本 / 需要真的跑一次 |
| `unmapped` | **0** | 每条都有探针或显式理由 |

7 条 `confirmed` 的实测（`.venv` Python 3.12.14）：

```

card 4  pytrec_eval=absent
```

**`stale = 0` 是好消息也是有效信息**：第 10 轮的转写没有写进过时的阻塞，Owner 若照这份列表做决定，不会被过期信息误导。这一点此前是未知。

## 3. 一处措辞误差：`pandas versions` 其实是「根本没有 pandas」

第 10 卡写的是 `datasetsforecast and pandas versions`，读起来像「版本待核」——即「装了，但版本不确定」。实测是 **`pandas` 完全不存在**（`find_spec` 返回 `None`）。

差别不是措辞洁癖：`版本待核` 会让人以为跑一次 `pip show` 就解决，`完全缺失` 才说明这张卡的评分环境根本没搭起来。同时这也解释了一件一直含糊的事——`.venv` 里 **numpy 2.5.4 / scipy 1.18.1 / pyyaml 6.0.3 都在，pandas 不在**，所以 M 系列的数值脚本能跑，而任何依赖 pandas 的路径（M4 评分、表格类配方）在本机不可跑。这条已写进清单的 `blocker_check.environment`。

## 4. 「授权装依赖就能解锁 P2」是假的：只解开 24%

29 条里 7 条是包缺失。剩下 22 条要的是**数据、许可、凭据、上游版本**，装包一条都解不开：

| 类别 | 例 |
|---|---|
| 需要数据集本身 | `fold-data hash and sample counts`、`M4 data and submission-118.zip`、`UCI data hash` |
| 许可问题 | `SciFact licence`、`data licence unknown` |
| 凭据 | `API key`、`paid OPENAI/TAVILY key`、`LLM tokens`、`model credentials` |
| 上游事实 | `release not pinned`、`comparison commit`、`rand_seed not pinned` |
| 要真的跑一次 | `runtime smoke`、`independent index (initialisation rebuilds it)` |

`runtime smoke` 这条还自指：它不是原因，是「没跑过」这件事本身。这种条目放进 blockers 会让人以为有外部障碍，其实只是缺一次执行——已按 `undecidable` 记，理由写明。

**给 Owner 的算式**：一次性授权装 7 个包 → 阻塞从 29 降到 22（−24%），且卡 4 仍被「没有 Elasticsearch 服务」挡着（装客户端不等于起服务）。所以「先把依赖装齐再说」不是通解。

## 5. `EXIT 0` 不能读成「已清空」

第一版把出口叫 `ALL_BLOCKERS_SETTLED`，而真实跑会给出 `EXIT 0` + 22 条 `undecidable`——那个绿会被读成「阻塞都清了」。改成 `MAPPING_COMPLETE`，并强制追加一行：

```
EXIT 0 (MAPPING_COMPLETE)
NOTE: 22 of 29 blockers are still undecidable. Exit 0 means the mapping
      is complete, NOT that these recipes can run.
```

这是本项目反复踩的同一个坑的正向应用：**让绿只表示它真正表示的那件事**。

## 6. 探针保真度的两处交代

- **客户端不是服务**：`elasticsearch` 模块缺失只能说明没有客户端，不能说明没有服务。所以对这条额外做本地端口探测（9200/9300，0.5 s 超时），实测两个端口都 `closed`，与客户端缺失是两个独立证据。自检 S9b 专门钉住「端口在听也不许因此削弱已确认的判定」。
- **`numpy benchmark tree` 不是 numpy**：numpy 装了（2.5.4），但这条指的是 asv 的 benchmark 仓库树，装没装 numpy 与它无关 → 归 `undecidable`，理由写明。若按字面匹配「numpy present」判成 `stale`，就是拿错的证据算出「卡过时」。

## 7. 自检与确定性

自检 **10/10**、退出码 0；真实跑两次输出逐字节相同（`1c1fd5f5…` 早版、现行版复跑一致）。规则：

| 规则 | 判什么 |
|---|---|
| R1 / R2 | `call_record=none` 或 `draft_only` 却 `blockers` 为空 → 自相矛盾（已对 10 张卡全部成立） |
| R3 | 每条 blocker 必须映射到探针 → 否则 `unmapped`，`EXIT 2`（不许静默漏） |
| R4 | 模块探针给出 `confirmed` / `stale`；多模块时**任一缺失即 confirmed** |
| R5 | 外部依赖记 `undecidable` 并写明理由 |
| R6 | 两次运行一致 |

映射表是**人工建的**（29 条逐条写），所以真正的风险是「新写的 blocker 措辞没人建探针」——这正是 `unmapped → EXIT 2` 存在的理由：它把「我没查」变成红，而不是变成绿。

## 8. 工具坑：用行前缀做 `old_string` 会切掉该行剩余部分

改这个脚本时，我用 `# Blockers that no local probe can settle` 作为 `old_string` 的结尾——它只是完整注释行 `# Blockers that no local probe can settle, with the reason kept explicit. The` 的**前缀**。替换后该行变成 `}, with the reason kept explicit. The`，直接是语法错误。

`Edit` 报成功、字节数变小，只有下一次 Read 才看见。教训：**锚点要取整行，不要取行的前缀**；改完立刻 Read 或用 `py_compile` 兜一次。本轮是靠 `py_compile` 前的 Read 拦住的。
