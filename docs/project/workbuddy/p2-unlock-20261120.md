# P2 的「跑一张卡就推一格」不成立：它是 10 次运行 + 2 枚版本锚（周期检查第 15 轮）

2026-11-20 · 零研究行动 / 零模型 / 零现金 / 零安装 / 零推送 / 平台用量 unknown

## 被检验的两句话

这两句写进了状态文档，是「P2 可以小步推进」这个判断的全部依据：

> `continuous-status.md`：**任一张卡跑通一次最小例 → 改两个字段 + 给日志路径 → 门禁自动少一条失败项。P2 的进度因此可量化，不必再讨论「是否通过」。**

> `current.md`：**P2 的缺口现在只剩「卡真跑过一次」这一件事。**

两句都没有被执行过。它们读起来像承诺，实际是一个**可证伪的机械断言**：填一张卡，失败项应该变少。本轮直接跑它。

## 为什么可能不成立

`scripts/p2_recipe_check.py` 里 R6/R7 是**全量规则**：

```python
for item in recipes:              # 十张卡逐张
    ...
results.append(record("R6_call_record", not missing_evidence and not no_record, ...))
```

任何一张卡缺调用记录，R6 就 FAIL。填一张卡**只能缩短它的 detail 字符串，不能让规则翻绿**。R5 又是另一根轴：它 FAIL 在 `anchor_strength == "weak"` 的两张具体卡上，跑最小例跟它没关系。

所以正确的预测是「填一张卡，失败集不变」。下面实测。

## 四个场景

场景全部是清单的深拷贝，写在 `runs/p2-unlock-20261120/`，**真实清单一字未改**。

| 场景 | 做法 | rc | 失败规则集 |
| --- | --- | --- | --- |
| A 基线 | 原样 | 1 | `R5_anchor, R6_call_record, R7_min_example` |
| **B 填一张卡** | 第 1 张给调用记录 + 已验证最小例 + 两个证据文件 | 1 | **`R5_anchor, R6_call_record, R7_min_example`（不变）** |
| C 填满十张 | 十张全给 | 1 | `R5_anchor` |
| D 填满 + 两枚锚版本化（**反事实**） | 再把 2 张 `weak` 抬到 `medium` | 0 | （无） |

**B 的明细解释了为什么**：R6 与 R7 各剩 **9 条问题**（`Fairlearn …: no call record; NumPy ASV …: no call record; …`），规则仍是 FAIL。第 1 张卡的那两条问题确实消失了——**但那只改变了 detail 字符串，没改变判定**。

## 判定

**「任一张卡跑通一次最小例 → 门禁自动少一条失败项」被证伪。**

准确说法是：

1. **运行轴**：需要 **10 次**真实最小例运行（全部十张卡），不是 1 次。C 场景证明十张填满后 R6/R7 才一起翻绿。
2. **版本轴**：另有 **2 枚版本锚**要落（`GPT Researcher Deep Agents`、`data-to-paper social_network`），跑最小例不会顺手解决。B/C 两场景都还挂着 `R5_anchor`。
3. **两轴独立**：C 只解运行轴仍 `rc=1`；D 才是 `rc=0`。所以「P2 的缺口只剩卡真跑过一次」这句话**漏掉了 R5 这条轴**。

## 让这件事更贵的一条输入事实

清单自带的阻塞分布（本轮从清单独立统计，不依赖第 14 轮的门禁输出）：

| 项 | 值 |
| --- | --- |
| 阻塞总数 | **29** |
| 卡数 | 10 |
| **零阻塞的卡** | **0** |
| 单卡阻塞范围 | **2–4 条** |

也就是说 **「跑通 10 次」这个动作本身，先要逐卡解开 2–4 条阻塞**；而第 14 轮已经量过：29 条里只有 **7 条**能靠装包解决（装齐只把 29 降到 22），其余是数据 / 许可 / 凭据 / 上游版本 / 必须真跑一次。

两轮合起来，P2 的真实形状是：**先解 ≥22 条非装包阻塞 → 再跑 10 次最小例 → 再补 2 枚版本锚**，而不是「跑一次就推进一格」。

## D 场景的边界（别读过头）

D 是**反事实**：它把两张弱锚假装成 `medium`，只为回答「这个门禁是不是压根不可能全绿（死门）」。答案是**不是死门**（另见门禁自检里「合成的全满足清单 → EXIT 0」）。**本轮没有任何证据表明那两枚版本锚真的存在或可取得**，不得据此说 P2 可达。

## 验证

- 与真实 CLI 交叉核对：`p2_recipe_check.py --json` 基线失败集 == 探针 A 场景失败集（`R5/R6/R7`），两边 `rc=1`
- 探针自检 **11/11**，退出码 0
- 连续两次运行输出**逐字节相同**
- 只读：只写 `runs/`（gitignored），真实清单与卡片未改

## 本轮自己踩的坑（保留）

首跑崩在 `Path.relative_to()`：证据目录是相对路径、仓库根是绝对路径。**退出码 1**——而该脚本「场景与期望不符」也是 **1**。崩了和判失败凭退出码分不开，只有 stderr 的 traceback 能分开。这就是同一份改动里 `round_align.py` 新增 `how=crashed` 的现实依据，两件事互相印证。

自检为什么没抓到：自检里 `root` 是绝对的临时目录、`evidence` 是 `root/"ev"`，两者都绝对，路径关系成立；真实调用里 `out_dir` 是相对字符串。**夹具的路径形状和真实调用的路径形状不一致**——这是「自检通过 ≠ 真实可用」的又一例，与第 12 轮「校验器假失败」同族。
